# 当前仓库时间对齐与六个月业绩审查

审查日期：2026-11-03。只读审查现有构建脚本及输出，未修改生产代码或数据。

## 对两个核心问题的回答

**收益和 alpha 都取截至 date 的最近一个完整自然半年，月份归属正确；整个面板尚不能认定为严格时间对齐、无未来信息。**

| 面板 date | 收益和 alpha 的评价月份 |
| --- | --- |
| 20240630 | 2024-01 至 2024-06 |
| 20241231 | 2024-07 至 2024-12 |
| 20260630 | 2026-01 至 2026-06 |

两类指标都要求六个月齐全，不足则缺失。当前原始月度数据与六个 alpha 输出均没有基金月份重复；因此计数为六确实对应六个不同月份。

- `raw_ret = [∏(1+r_m)]^(1/6) - 1`：这六个月的几何平均月收益，小数制。不是六个月累计收益。累计收益可由 `(1+raw_ret)^6-1` 恢复。
- `*_alpha = mean(alpha_m)`：这六个月的单月风险调整收益算术均值，小数制，没有年化。
- `alpha_m = r_m - rf_m - beta_hat_(m-1)'F_m`，每个月的 beta 用此前连续24个月估计，回归含截距，评价月不进入其自身 beta 估计。
- 当前导出到面板的 alpha 不是六个月回归截距，也不是24个月历史回归截距。后者在月度输出里叫 `a_hat`。

例如2024年1月的 beta 用2022-01至2023-12，2024年6月的 beta 用2022-06至2024-05；再将2024年1至6月的 alpha 取均值。因此评价期是六个月，但计算需要更早的历史收益。

实例：`000006 / 20240630` 的 `raw_ret=-0.04133706998352615`，即平均每月约-4.1337%；对应六个月累计收益约-22.3761%。

## 必须修复或在实证前明确处理的问题

### 1. [P1] 无半年报时将年报发生额直接标为下半年，期间与收益不一致

位置：`merge_buy_sell_zero.py:109-115`；`merge_fee.py:80-96`。

代码遇到同年半年报缺失，会直接把年报数放在1231行，不检查年报起点是否早于7月1日。于是7至12月收益对应的买卖金额、费用可能是全年或超过六个月的累计发生额，影响换手率、费用率及其与业绩的比较。

实测最终面板：

- 买卖金额783行统计起点早于7月1日，全部在2010年及以后。
- 费用717行存在此问题，其中610行在2010年及以后。这个数量是匹配到最终面板后的数量；原始费用报告中有767条，不应混用。
- 例如`000021 / 20101231`的买卖起点是2010-01-01，买入约276.85亿元，却被标为H2。
- 例如`000066 / 20131231`的费用起点是2013-01-01，费用12,859,747.40元直接并入该半年；该行收益只取7至12月。

最小修正：缺少半年报、且年报起点早于7月1日时，半年发生额留空，不用全年值代替；起点晚于7月1日时要明确是非完整半年。保留原始年报另作追溯。

### 2. [P1] 转型未分段，24个月估计窗口混入转型前策略

位置：`rolling_alpha.py:98-108`、`rolling_alpha.py:124-133`、`rolling_alpha.py:156-159`；`build_fundid_date.py:88-94`。

`load_inception()`只读`成立时间_earliest`；它的注释声称该日期是转型日，但这不对所有基金成立。滚动窗口仅按缺失和日历断点分段，没有按转型事件分段。README已提示此限制，但代码尚未处理。

实测`003853`的earliest为2017-03-10，latest为2018-04-18；仓库记录其2018年4月由纯债转为股票基金。2019-12的现有CAPM alpha使用2017-12至2019-11的24个月历史，仍含转型前债券策略。`000646 / 2019-12`也使用2017-12至2019-11，跨越2019年9月转型。

最小修正：先核实实质策略变化的生效日，再按基金×策略阶段分段；窗口不得越过阶段边界。不能直接用latest替代所有成立日，因为两列只是不同来源日期的最大最小值，尚不保证每个latest都是转型日。单纯更名也不应机械切段。

### 3. [P1，预测使用时] 报告截止日匹配不等于当时可获得

位置：`merge_total_equity.py:47-52`、`merge_holder_ratio.py:93-98`、`merge_fee.py:117-122`。

财务、持有人和买卖字段都按`EndDate=date`接入，没有公告日期或可用日期过滤。例如0630行的半年报变量，代码不检查该报告是否在0630前已公布。因此，该表可用于报告期归属的事后描述，但不能直接把同一期财报控制变量视为期初或期末已经公开的信息。

最小修正：明确回归中的决策时点，按公告/可用日选取当时已知的最近一期数据。仅将alpha换成下一自然半年仍不足以保证该半年起点时所有解释变量已经公开。此项没有逐条复核原始公告日期，不能据当前代码给出具体泄漏行数。

### 4. [P2] 最终面板没有执行2010年正式样本下界

位置：`build_fundid_date.py:64-76`；`merge_alpha.py:125-133`。

生成日期只检查成立日和样本上界，最终合并也没有过滤2010年前观测。现有最终输出45,929行，最早20021231；其中1,119行早于2010年，337行已有CAPM alpha。仓库`名单CSMAR匹配/使用说明.md`明确正式研究期间是2010-01-01至2026-06-30。

最小修正：保留预样本月度数据供估计，在最终研究样本导出时过滤正式日期。若本表仅作为历史中间表，则应明确标注，并另有执行该过滤的正式样本出口；当前主构建链未见这个出口。

## 还需处理的时点口径

### 5. [P2] 从业年限是任期行快照，没有按面板日期变化

位置：`merge_fund_manager.py:155-167`。

在职任期过滤本身按历史日期执行，但`midAge/largeAge`直接聚合源表的固定`BusinessDuration`。实测`163406`中谢治宇的源任期2013-01-29起，BusinessDuration为6；20130630、20151231、20181231、20201231四个面板时点的midAge和largeAge都为6。这些变量不能直接解释为“当期证券从业年数”。

修正前先核实BusinessDuration的计量基准日；若能获得证券从业起始日期，则按各期日期计算。没有基准日时保留为任期记录快照或缺失，不凭任职日推定其从业年限基准。学历同样缺少历史取得日期，本次没有确认其是否存在历史回填。

其他口径：当前“建仓月”处理只剔除成立月起第一个非空增长率月份，不是剔除六个月建仓期。例如000006的2019-04被剔除、2019-05起进入样本。如果研究设计要求成立后六个月建仓期代理，现有代码没有实现。期末经理团队也是期末快照，不能直接解释为管理了整个半年。

无风险利率采用月末最新存款年利率折月；变更日没有晚于该月月末，但月内变更时将月末利率用于整月，未按生效日分段。它是月末报价折月口径，是否与CSMAR因子内部的无风险处理完全一致，本次没有重新核实方法说明书。
